## 〇、一句话摘要

> 送出去的东西，要能一直修、一直升、一直查得到出处——否则就是一次性赠品，不是资产。

---

## 第 1 章 范围与术语

### 1.1 适用范围

本规范适用于任何向外部用户供应可升级技能包/插件/工具包的组织或智能体，包括：

- 向用户发放的技能包（Skill Pack）
- 向用户发放的智能体能力包（Agent Capability Pack）
- 赛事发放的奖品型工具包
- 企业内部统一分发的工具链

### 1.2 术语定义

| 术语 | 定义 |
| --- | --- |
| 技能包 | 可分发的、封装特定能力的最小交付单元 |
| 出厂三样 | 清单（manifest）、升级指南（upgrade-guide）、版本谱系（changelog） |
| 供应方 | 发放技能包的主体 |
| 接收方 | 获得技能包的使用者 |
| 升级通道 | 接收方获取新版本的稳定入口 |

---

## 第 2 章 出厂三样（核心）

任何对外供应的技能包，必须随包提供以下三样，缺一即不合规。

### 2.1 清单（manifest）

| 要求 | 说明 | 判据 |
| --- | --- | --- |
| M1 唯一标识 | 技能包有唯一名称与标识 | 存在 name 且唯一 |
| M2 版本号 | 遵循语义化版本 | 存在 version |
| M3 能力声明 | 声明提供的能力与触发场景 | 存在 capabilities / description |
| M4 依赖声明 | 声明运行依赖与兼容环境 | 存在 dependencies / 兼容说明 |
| M5 许可证 | 明确许可证标识（SPDX） | 存在 license |
| M6 完整性指纹 | 提供内容哈希 | 存在 SHA-256 |
| M7 升级通道 | 提供新版本获取地址 | 存在 upgrade_url |

### 2.2 升级指南（upgrade-guide）

| 要求 | 说明 |
| --- | --- |
| U1 安装方法 | 明确、可复制执行的安装步骤 |
| U2 升级方法 | 明确升级步骤与前置条件 |
| U3 版本差异说明 | 新旧版本差异摘要 |
| U4 回滚方法 | 出问题如何退回旧版 |
| U5 卸载方法 | 如何干净移除 |
| U6 常见问题 | 已知问题与处理 |

### 2.3 版本谱系（changelog）

| 要求 | 说明 |
| --- | --- |
| L1 版本列表 | 完整版本历史 |
| L2 变更类型 | 标注修订/功能/主版本 |
| L3 日期 | 每版发布日期 |
| L4 兼容性 | 标注是否向后兼容 |

---

## 第 3 章 版本语义（红线）

核心要求：版本号必须传达兼容性信息，不得随意递增。

| 版本位 | 递增条件 | 接收方须做什么 |
| --- | --- | --- |
| 修订版x.y.Z | 仅修复缺陷，不改行为 | 可直接替换，无需阅读变更说明 |
| 功能版x.Y.z | 新增能力，向后兼容 | 须阅读变更说明后更新 |
| 主版本X.y.z | 不兼容变更 | 须重新登记（衔接 SPEC-002 第 3 章） |

> 红线：不得用修订版号发布不兼容变更。 这是对接收方信任的透支。

## 第 5 章 供应链完整性

### 5.1 发布前检查

供应方在每次发布前须确认：

1. 清单字段完整（第 4 章）
2. 文件哈希与实际内容一致
3. 无明文密钥（自动扫描）
4. 许可证与依赖合规
5. 升级通道可达

### 5.2 接收方验证

接收方可独立验证：

获取技能包 → 计算哈希 → 比对清单 → 校验许可证 → 确认升级通道 → 安装

### 5.3 升级通道稳定性承诺

| 承诺项 | 要求 |
| --- | --- |
| 通道可用性 | 供应方应保证升级通道长期可达 |
| 旧版本可获取 | 至少保留最近 N 个版本的获取途径（N 建议 ≥ 3） |
| 变更可预告 | 主版本变更应提前告知 |
| 停供须声明 | 若停止供应，须公开声明并提供迁移路径 |

| 对齐对象 | 对齐关系 | 边界声明 |

## 附录 A：与 UIBC 赛事的关系

本规范是 UIBC 奖品发放的技术依据：

- 发放给获奖者的专家型 Agent 须满足完备符合性；
- 升级通道须在赛事结束后继续可用（奖品不是一次性交付）；
- 接收方可通过验真入口核验奖品真实性（衔接 SPEC-002）。
